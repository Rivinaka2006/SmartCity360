## 2. Pattern evidence

### A. Decorator — secured energy streams

**Problem and structure.** A meter payload needs configurable, ordered security/transformation layers without a subclass per combination. `EnergyDataStream.process(StreamContext)` is the component; `RawEnergyDataStream` is the base; abstract `StreamDecorator` implements the component and composes exactly one `delegate`. `AuthenticationDecorator`, `CompressionDecorator`, and `EncryptionDecorator` extend it. `EnergyStreamPipelineFactory.create` begins with raw data and successively wraps it according to `ProcessingLayer` values; it rejects absent authentication, duplicates and invalid ordering. Supporting paths: `.../energy/stream/EnergyDataStream.java`, `StreamDecorator.java`, `RawEnergyDataStream.java`, `AuthenticationDecorator.java`, `CompressionDecorator.java`, `EncryptionDecorator.java`, `EnergyStreamPipelineFactory.java`.

Representative implementation: `AuthenticationDecorator.process` authenticates then delegates and appends `AUTHENTICATION`; compression and encryption delegate first, then append GZIP or AES-GCM output. This is flexible layering: `[AUTHENTICATION]`, `[AUTHENTICATION, COMPRESSION]`, and `[AUTHENTICATION, COMPRESSION, ENCRYPTION]` use the same types.

**Security/runtime flow.** `POST /energy/streams/process` decodes request payload/proof into `EnergyProcessCommand` (`EnergyStreamResource.process`). `EnergyStreamServiceBean.process` checks meter status/key-version, constructs `MeterProof` and `StreamContext`, invokes the factory, and records success/failure. `MeterAuthenticator.authenticate` resolves an HMAC-SHA256 meter key, constant-time compares canonical HMAC and invokes `InMemoryReplayProtector.accept`; the protector enforces a 300-second window, nonce uniqueness and bounded 100,000-entry memory. `AesGcmEnvelope.encrypt/decrypt` uses AES/GCM/NoPadding, 12-byte random nonce, 128-bit tag and key-ID AAD; `PayaraKeyProvider` resolves Base64 configuration values via MicroProfile Config and validates 32-byte keys. `EnergyStreamRunRecorder.record` uses `REQUIRES_NEW` to retain processing history in `energy_stream_runs` on success or failure.

**REST/data/tests/UML-ready.** Endpoints are `POST /energy/streams/process` (machine HMAC request), `POST /energy/streams/verify` (ADMIN/CITY_MANAGER enforced by service), and `GET /energy/streams/runs[/{id}]` (ADMIN/CITY_MANAGER/SUPERVISOR service role): `EnergyStreamResource`, `EnergyStreamServiceBean`. DTOs: `ProcessBody`, `VerifyBody`, `ProcessResponse`, common `EnergyProcessCommand/Result/RunView`. Tables are `energy_meters` (credential key-id/version added by V005) and `energy_stream_runs` (meter FK; decorator chain JSONB): V002/V005. UML: `EnergyDataStream <|.. RawEnergyDataStream`; `EnergyDataStream <|.. StreamDecorator`; `StreamDecorator <|-- AuthenticationDecorator|CompressionDecorator|EncryptionDecorator`; `StreamDecorator 1 --> 1 EnergyDataStream delegate`; factory creates nested components; service uses factory/recorder. Tests: `EnergyStreamPipelineTest`, `PayaraKeyProviderTest`, `EnergyStreamServiceSecurityContractTest`, `MeterIngestionBoundaryTest`.

Benefits are combinatorial reuse and a single pipeline validator. Limitations: fixed allowed layer list/order, in-memory replay state is node-local/non-durable, and key material requires external Payara configuration. `database/tests/Invoke-EnergyStreamIntegrationTests.ps1` deliberately asks the operator to restart Payara manually and never restarts it itself.

### B. Composite — hierarchical zones

**Problem and structure.** CITY → DISTRICT → STREET → BUILDING must receive the same tree/usage/power operations while only buildings make physical state changes. `ZoneComponent` declares `children`, `shutdown`, `restore`, `reportUsage`; `CompositeZone` holds `List<ZoneComponent>` and recursively aggregates/delegates; `BuildingLeaf` returns no children and applies its `PowerOperationContext` callback. `CompositeZone.add` accepts only `kind.childKind()` and rejects duplicates. Exact sources: `.../zones/domain/composite/ZoneComponent.java`, `CompositeZone.java`, `BuildingLeaf.java`, `ZoneKind.java`, `PowerOperationContext.java`, `UsageQuery.java`.

`ZoneTreeAssembler.load/assemble` converts `ZoneRepository.findSubtree` rows to either `CompositeZone` or `BuildingLeaf`, then attaches children. `ZoneServiceBean.power` loads the composite, locks buildings, provides a persistence state-changer callback, invokes `root.shutdown/restore`, and writes a `zone_commands` history row. `usage` aggregates readings per building and calls `root.reportUsage`.

**UML-ready specification (Part B).** `ZoneComponent` interface `{id, code, name, kind, children(), shutdown(ctx), restore(ctx), reportUsage(query)}`; `CompositeZone implements ZoneComponent`, composition `CompositeZone 1 *-- 0..* ZoneComponent children`; `BuildingLeaf implements ZoneComponent` and has `0` children. `ZoneTreeAssembler --> ZoneComponent` creates the concrete forms. Domain cardinality is CITY `0..*` DISTRICT, DISTRICT `0..*` STREET, STREET `0..*` BUILDING, each non-CITY child `1` parent; sources above plus `ZoneTreeAssembler.java`, `ZoneEntity.java`, V004.

REST: `GET /zones`, `/{id}`, `/{id}/tree`, `/{id}/path`, `/{id}/usage`, `/{id}/commands`; ADMIN creates/updates/deactivates; ADMIN/CITY_MANAGER POST `/{id}/shutdown|restore`: `ZoneResource`. Relevant tables: self-referential `zones`; `building_power_states`, `zone_commands`, `energy_meters`, `energy_readings`. V004 trigger validates parent-type chain/cycles and requires meter→BUILDING/streetlight→STREET. DTOs: `ZoneTreeView`, `ZoneView`, `PowerOperationView`, `UsageView`. Tests: `ZoneCompositeTest`, `ZoneTreeAssemblerTest`, `ZoneServiceContractTest`, `ZoneParentLookupTest`, `UsageReadingAggregatorTest`, `ZoneResourceContractTest`.

Benefits are uniform recursive commands and local leaf behavior; persistence enforces hierarchy. Limitations: tree assembly/operations load an entire subtree; the four-level domain is intentionally fixed; power history reports aggregate results rather than per-leaf command rows.

### C. Chain of Responsibility — complaint routing

**Problem/flow.** On submission or escalation, severity/target level is routed through LOCAL_STAFF → SUPERVISOR → CITY_MANAGER without `ComplaintServiceBean` selecting concrete handler branches. `ComplaintHandler.route`; `BaseComplaintHandler` contains `next`, accumulates a trace and delegates when `canHandle` is false; three concrete handlers only define `level`. `ComplaintChainFactory.standardChain/build` constructs and validates the chain. Sources: `.../complaints/domain/chain/*.java`.

`ComplaintServiceBean.submit` routes `ComplaintRoutingContext.initial(severity)`, persists `current_handler_level`, and adds a SUBMITTED event with route note. `escalate` calls the same chain from `current.next`, clears assignment, changes status and appends an ESCALATED event. REST in `ComplaintResource`: resident POST `/complaints`; staff/admin queue, assign, start, escalate, resolve and history endpoints (method-level roles in source). Tables: `complaints` (resident/zone/assignee FKs, severity/status/current handler), `complaint_events` (from/to level and note) and `audit_logs`; see `ComplaintEntity.java`, `ComplaintEventEntity.java`, V002. Tests: `ComplaintChainTest`, `ComplaintServiceContractTest`, `ComplaintResourceContractTest`, `ComplaintViewJsonTest`.

UML-ready: `ComplaintHandler <|.. BaseComplaintHandler`; `BaseComplaintHandler <|-- LocalStaffHandler|SupervisorHandler|CityManagerHandler`; `BaseComplaintHandler 0..1 --> BaseComplaintHandler next`; factory creates chain; route returns `RoutingDecision` containing selected level and trace. Benefits: handler ordering is factory-configurable and the persisted event trace aids auditability. Limits: handlers currently differ only by enum level; standard factory is recreated per action and rules are static code, not configured workflow.

### D. Flyweight — shared lighting profiles

`StreetlightFlyweight` provides `apply(context, command)` and `effectiveBrightness`. Immutable `SharedLightingProfile` record is the concrete flyweight; application-scoped `LightingProfileFactory` caches by immutable `ProfileKey(profileId, version)` in bounded access-order LRU (capacity 1,024), with hit/miss/eviction/context counters. Sources: `.../streetlights/domain/flyweight/StreetlightFlyweight.java`, `SharedLightingProfile.java`, `LightingProfileFactory.java`, `ProfileKey.java`, `StreetlightContext.java`.

Intrinsic shared state is profile key, manufacturer, model, wattage, default brightness, controller type, firmware family and config JSON. Extrinsic/per-light state is `StreetlightContext`: light and street-zone IDs, coordinates, label, operational state and brightness override; the command is also supplied at call time. `StreetlightServiceBean.shared` resolves/caches a snapshot; `operate` passes the individual context, persists changed state, and `statistics` exposes counters. It does not claim measured savings: benchmark test exists but normal Surefire excludes tag `benchmark` (`backend/pom.xml`).

REST: `/lighting-profiles` create/list/version/deactivate and `/streetlights` list/register/detail/profile/stats plus `/{id}/on|off|brightness|profile`: `LightingProfileResource`, `StreetlightResource`; roles are visible in their annotations. Tables: `lighting_profiles` and `streetlights` (many lights → one profile and → one STREET zone), V002. Tests: `LightingProfileFactoryTest`, `StreetlightFlyweightTest`, `StreetlightServiceContractTest`, `StreetlightFlyweightBenchmarkTest` (benchmark-tagged), `StreetlightResourceContractTest`. UML: `StreetlightFlyweight <|.. SharedLightingProfile`; factory `1 *-- 0..1024 SharedLightingProfile`; `StreetlightServiceBean --> factory`; flyweight `apply(StreetlightContext, LightCommand)`. Benefits: stable immutable profiles shared/cached and versioned keys avoid stale snapshots. Limits: per-process cache is not distributed and can evict; configuration/profile edits are version/new-row operations rather than mutation of shared instances.

### E. Interpreter — versioned operational-policy DSL

`Expression` is sealed and interpreted against `EvaluationContext`; concrete AST nodes are `ComparisonExpression`, `AndExpression`, `OrExpression`, `NotExpression`. Sealed `Operand` covers `VariableOperand`, numeric/string/boolean literals. `DslLexer.tokenize` recognises identifiers, quoted strings, numbers, booleans, parentheses, `> >= < <= == !=`, AND/OR/NOT. `DslParser.parse` grammar precedence is OR → AND → NOT → parenthesized/comparison; it validates domains/variable types and source/token/node/depth limits. Sources: `.../policies/domain/interpreter/Expression.java`, `Operand.java`, `DslLexer.java`, `DslParser.java`, `DslLimits.java`, `PolicyVariableRegistry.java`, all expression/literal classes.

**UML-ready specification (Part E).** `Expression {interpret(EvaluationContext): EvaluationResult}`; `ComparisonExpression`, `AndExpression(left,right)`, `OrExpression(left,right)`, `NotExpression(expression)` implement it. `ComparisonExpression` associates two `Operand`; `Operand {resolve, type, display}` is implemented by variable/literal types. `DslParser --> DslLexer`, registry and limits; it creates AST. `PolicyServiceBean --> DslParser`; `PolicyVersionEntity 1 --> 1 PolicyEntity`, and `PolicyEvaluationEntity 1 --> 1 PolicyVersionEntity`. Supporting persistence sources: `PolicyEntity.java`, `PolicyVersionEntity.java`, `PolicyEvaluationEntity.java`, V002.

`PolicyServiceBean.createVersion` persists immutable numbered DSL source and validation outcome; `validateVersion` reparses; `activateVersion` deactivates existing active versions then activates a valid target in a transaction; V002 partial unique index permits one active version per policy. `evaluate` parses the active version, builds typed context, interprets, records result/error/duration and returns an explanation tree. REST: `POST/GET /policies`, versions, validate, activate, evaluate, deactivate and evaluations: `PolicyResource`; managers create/manage; all operational roles can evaluate. DTOs are `PolicyCreateCommand`, `PolicyVersionCreateCommand`, `PolicyEvaluationCommand` and respective views. Tests: `DslInterpreterTest`, `PolicyServiceContractTest`, `PolicyResourceContractTest`.

Benefits: rule text changes through version/validation/activation rather than a redeploy; typed parsing, bounded complexity and explanation tree support safe evaluation. Limits: grammar/variables/domains remain code-defined, no user-defined functions, and source AST is parsed per evaluation (no persistent compiled-AST cache).

## 6. Final assessment evidence refresh — 2026-11-10

### Architecture, deployment, and database clarification

**VERIFIED FROM SOURCE.** The Maven reactor contains six projects: root reactor, backend aggregator, and common/EJB/WAR/EAR modules. The root fixes Java release 17; the backend declares Jakarta EE 10.0.0, JUnit 5.13.4, MicroProfile Config 3.1.1, and Surefire 3.6.1 (`pom.xml`, `backend/pom.xml`). `smartcity360-common` supplies contracts, the EJB module owns service/persistence implementations, the WAR owns JAX-RS/security boundaries, and the EAR packages the common JAR, EJB JAR, and WAR at `/smartcity360` (`backend/smartcity360-ear/pom.xml`, `application.xml`).

The React SPA is **not packaged into the EAR**. `frontend/vite.config.ts` creates an HTTPS Vite development server at `https://localhost:5173`, only when Vite is invoked with `serve`, and proxies `/smartcity360/api` to `https://localhost:8181`. Its production build emits frontend assets separately; neither the source nor the observed health response proves a particular production SPA hosting arrangement.

JPA uses JTA persistence unit `smartcityPU`, datasource JNDI name `jdbc/smartcity360`, and disables JPA schema generation (`persistence.xml`). V001–V005 are the committed migration sequence: migration ledger, application schema, role seed, zone invariants, and meter credential references. PostgreSQL is evidenced by SQL syntax and migration design, but the physical database name is **NOT VERIFIED / REQUIRES CONFIRMATION**: a JNDI datasource name is not proof of its configured database name. For ERD work, draw `users`—`user_roles`—`roles`; self-referencing `zones`; `complaints`/`complaint_events`; `lighting_profiles`—`streetlights`; `energy_meters`—`energy_readings`/`energy_stream_runs`; `policies`—`policy_versions`—`policy_evaluations`; `building_power_states`, `zone_commands`, and `audit_logs`, with the foreign keys and indexes in V002/V005.

### Security, audit, and module evidence

**VERIFIED FROM SOURCE.** `AuthResource` implements CSRF-token issue, login, current-user lookup, and logout at `/auth/csrf`, `/auth/login`, `/auth/me`, and `/auth/logout`. Login normalizes email, rotates the session ID, applies `LoginThrottle`, clears the password character array, and delegates to Jakarta Security; logout records the event, invokes servlet logout, then invalidates the session. `PasswordHasher` uses salted PBKDF2-HMAC-SHA256 with 600,000 iterations; session cookies are HttpOnly, Secure, and SameSite=Strict with 30-minute timeout (`PasswordHasher`, `AuthResource`, `web.xml`, `payara-web.xml`).

`CsrfRequestFilter` requires a session CSRF token plus matching Origin/Referer on unsafe requests. The machine-meter ingestion boundary is the narrowly coded exception; it is protected by its own HMAC/replay controls, not by a browser session. `@RolesAllowed` exists on JAX-RS resources and EJB services; the SPA's `route-policy.ts`/`RoleRoute` limits navigation and presentation only, while server-side checks remain authoritative. `UserManagementServiceBean` additionally prevents an administrator from changing their own roles or disabling/suspending themselves and protects the last active administrator; it validates page limits, email, role existence, minimum 14-character password, and request state.

`SecurityAuditService` persists security events in independent `REQUIRES_NEW` transactions and application events in the caller transaction to `audit_logs`; `ComplaintEventEntity`, `ZoneCommandEntity`, `EnergyStreamRunEntity`, and `PolicyEvaluationEntity` provide module-specific histories. There is no inspected JAX-RS audit-log query resource or dedicated frontend audit-log page, so audit persistence must not be represented as a user-facing audit viewer. Relevant UI histories are complaint history, zone command history, energy run history, and policy evaluation/version history.

The remaining completed module evidence is: Dashboard (`DashboardPage`, `DashboardResource`, `DashboardServiceBean`); users (`UsersPage`, `UserManagementResource`, `UserManagementServiceBean`); health (`HealthResource`, `HealthServiceBean`); and the five pattern modules documented above. For screenshot planning, capture an ADMIN login/current user and logout; an operational dashboard summary; each module's record/history view; and role-boundary responses separately. Do not use a resident dashboard-summary screenshot as proof of backend authorization.
